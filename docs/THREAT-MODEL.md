# Threat model

## Assets and trust

Protected assets are source database/content data, source bearer credentials, sandbox-local identity/configuration, active sandbox files/tables, and external production services. A paired sandbox is trusted to receive source data. A source is trusted to provide executable plugin/theme code. Neither trust assumption permits escaping configured roots, bypassing TLS, racing activation, or silently accepting partial data.

## Enforced controls

- Public sources require verified HTTPS; local certificate overrides are explicit and target-based.
- Pairing codes expire and are consumed atomically. Stored sandbox tokens are sealed with local key material; source tokens are hashed, revocable, expiring and audited.
- Bulk export requires an expiring random transfer ID bound to the bearer and scoped to selected database/directories/constants/tables. Its 12-hour idle lease slides on activity; expired-session recovery is permitted only for the same bearer, ID and reconstructed exact job scope.
- Request bodies, cursors, responses, manifests, table counts, statement sizes, decompression and measurable filesystem staging capacity are bounded.
- Archive paths are canonical, component-safe and checksum validated. Incremental uploads are hashed during source streaming; a bearer-keyed HMAC binds the trailing file manifest to the exact transfer request, and the bounded sandbox stage independently hashes every extracted byte before atomic installation. The explicitly destructive first baseline trades those per-file hashes for speed: authenticated HTTPS, tar header/framing checks, exact selected-scope enforcement, complete-file size checks, atomic visibility and a generation-checked final delta are its integrity boundary. Each finished baseline group commits its partitions to the per-partition cursor immediately with plan-time generations, so a later failure never re-copies completed years. A partial group is not marked applied; its atomically installed paths are retained behind a durable per-path resume cursor. Code directories activate only from a complete hashed stage with rollback retained.
- One fenced lease owns mutation. Chunk data and its resume cursor commit atomically. Cleanup uses exact registered resources.
- Full database imports validate source schema, authenticated chunk hashes, decoded statement shape, exact per-chunk row counts, and shadow-table creation before one atomic activation. A post-import source checksum comparison reports live drift but is not a global snapshot guarantee because the source remains writable. Posts/postmeta row delta instead validates its bounded row responses and applies them to a clone of the prior sandbox table; those mixed shadows cannot be meaningfully compared to one whole-source checksum.
- Schema-only policy transfers no source rows; its integrity-checked empty schema joins the same atomic activation and rollback mapping. The policy is explicit per table, and WordPress identity tables cannot use it.
- Email and WordPress HTTP calls are blocked before cloned code/data activation. Database activation and safety run behind an early-load 503 guard; failures roll back.
- The shell database fast path is off unless each site explicitly opts in (`SANDBOX_SYNC_ALLOW_SHELL_DB` / filter). It never passes a shell-parsed string: `mysqldump`/`mysql` receive argv arrays whose only request-derived element is a table name that must match `^[A-Za-z0-9_]+$` *and* the transfer session's scoped table list. Credentials travel in the process environment (`MYSQL_PWD`), never argv; `--no-defaults` prevents option-file injection. The sandbox re-hashes the full dump against the source's completion trailer (which must match its full line exactly and appear exactly once), requires the gzip stream to reach a clean `ZLIB_STREAM_END`, bounds both per-line and total decompressed size, restricts non-INSERT lines to the mysqldump preamble whitelist (rejecting all `GLOBAL`/`PERSIST`-scope statements, including inside versioned conditional comments), anchors INSERT rewriting to the exact backtick-quoted head, enforces that every forwarded line contains exactly one statement (a `;` outside a string literal is only legal as the final character, blocking statement smuggling behind a valid INSERT head), and imports through `mysql` batch mode that aborts on the first failed statement. Rows land in an attempt-unique staging table published by atomic `RENAME` only after the import process exited cleanly and the fenced lease was re-verified, so an orphaned import child from a lost lease can never write into a successor's shadow. Any deviation drops the partial staging table and reverts to the chunked JSON path.

## Residual infrastructure requirements

WordPress hooks cannot intercept plugins that open raw sockets, invoke system binaries, use direct SMTP, or access external services through infrastructure sidecars. Production deployments therefore require network-level egress denial with explicit source/observability allowlists. `blog_public=0` and noindex headers are not access control; use private ingress or authenticated access. Host/database backups remain mandatory. Database quota and free-space monitoring are hosting-platform responsibilities because managed database storage is not visible to the PHP runtime; capacity exhaustion can fail a shadow import but cannot activate an unvalidated database.

## Residual protocol limits

- The live site is not frozen. Tables and files are sampled at different times, so application-wide point-in-time consistency requires an external snapshot provider.
- The fast first uploads baseline deliberately does not carry per-file payload hashes. Its authenticated TLS/framing/size/atomic-write boundary detects truncation and structural corruption, but it is weaker than the per-file SHA-256 path used by incremental transfers. The final generation delta covers source changes during the copy, not arbitrary undetected corruption inside a size-correct baseline payload.
- Uploads generation tracking observes WordPress filesystem/media hooks, not raw SFTP, shell, or external object-storage changes. Operators must request a full uploads audit after out-of-band writes.
- Posts/postmeta row delta uses `ID` and `post_modified_gmt`; direct database writes or plugins that bypass normal post-modified semantics can escape that fast detector. A full sync/audit is the recovery path. The delta also clones full destination tables, so it reduces network traffic rather than database copy, binlog, or temporary-capacity cost.
